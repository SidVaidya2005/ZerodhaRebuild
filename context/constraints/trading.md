# Constraints — Money, orders, and the order engine

> Read this part of `context/constraints.md` before changing money logic, an order, or a
> Postgres money function. `trading-contract.md` is always read and decides every money
> rule. This reference explains the reasons behind those rules, their implementation,
> and the concurrency limits that still matter.

## Charges and the trading contract

The section references below point to `trading-contract.md`. Use that contract for the full rule;
these notes explain mistakes that a future change must avoid.

- Every bare `RAISE EXCEPTION` uses SQLSTATE `P0001`. Catching `when sqlstate 'P0001'` therefore also catches unrelated failures from callees or triggers. Money functions use the private code `ZR001` for controlled rollback instead; a structural test checks the live definition. (Phase 5 checkpoint)
- A short cover's collateral release must name the order that caused it, because §12.9 reconciles ledger rows by order. `recompute_position_collateral` once accepted no order id, leaving correct cash movements unattributable: the INFY short's rows summed to −4708.62 instead of its −18.19 cash effect, while the long reconciled exactly. The implementation was fixed to match the contract's inclusion of `MARGIN_RELEASE`. Changing the signature requires dropping the function, which loses its ACL and lets Supabase restore default grants; repeat the revokes. (Phase 4 checkpoint)
- Define §6's collateral formula only in `short_collateral_requirement()`. `reserve_margin`, `transfer_margin_to_position` and `recompute_position_collateral` all call it. Duplicating the formula risks releasing the wrong amount on a partial cover. (F23)
- Settle a flip's closing `SELL_CREDIT` before retiring its reservation, so its own sale proceeds can fund the new short. Keep both inside a `begin/exception` subtransaction. If collateral is still insufficient, roll back the attempted fill: simply marking it `REJECTED` would leave a credit for a sale that never happened, even while identity 1 still appeared to hold. §7 permits this sequence. (Phase 4 checkpoint)
- The guaranteed close applies to pure covers and square-offs. A flip also opens exposure, and §1 forbids partial fills, so insufficient collateral for that opening leg rejects the whole fill. §6 and the corrected `execute_order` comment state this narrower guarantee. (Phase 4 checkpoint)
- `transfer_margin_to_position` handles collateral increases; `recompute_position_collateral` handles releases. Run the transfer before writing trade and position rows, so a shortfall leaves neither to undo. It alone derives the gross `entry_reference_price` basis; callers store the returned value without recalculating it, as §12.11 requires. (F23)
- Reserve a short's collateral at placement. Reserving only 100% of notional against a requirement of 120% plus charges made `delta` positive on every short and allowed a maximum-size order that its own fill then rejected. (F23)
- Fund the covered quantity from existing short collateral; reserve fresh cash only for opening exposure and the charges required by §6. An MIS sell crossing zero reserves only the shorting excess. Without both rules, a user who shorted most of their balance could be unable to close it. (F23, fixed at F24)
- On a short cover, reported P&L and settled cash use different bases; see §7 and §12.11. Using `average_price` for cash settlement charges the entry fees twice and breaks identity 1. (F24)
- A short entry writes three ledger rows, as §6 steps 4 and 6 specify. The paired charge rows show that estimated charges were not paid twice; do not hide them by netting inside the function. (F23)
- When a fill crosses zero, split charges pro-rata by quantity. Round the closing share and assign the remainder to the opening leg, so they sum exactly to `trades.charges`. (F24)
- `modify_order` calls `reserve_margin` inside a plpgsql subtransaction instead of calculating a requirement itself. A failed re-reservation rolls back that block and keeps the original terms. Release first: `reserve_margin` returns early if `blocked_margin <> 0`. (F27)
- The success toast gets its fill price from one additional RLS-scoped `orders` read after `COMPLETE`. Widening `place_order`'s return for that string would require a migration to a function already tested at three tiers. (F26)
- `place_order` returns `(order_id, status, rejection_reason)`. Business rejections return normally with `error` null, so a uuid alone could not distinguish rejection from fill. Raising an exception would roll back the `REJECTED` row required by §4. (F24)
- Keep exactly two session implementations: `_shared/market-hours.ts` and Postgres `market_state(at)`. Tier 4 proves they agree. Since `authenticated` can call `place_order` directly by RPC, a Server Action's session check alone is insufficient. Do not add a third implementation. (F24)
- `execute_order` checks quote age using §5's staleness window. `market_constants()` mirrors `_shared/market-constants.ts`, just as `charge_rates()` mirrors the charge table. Without that check, a Monday order could fill at Friday's close. (F24)
- Keep Postgres charge rates in the single `IMMUTABLE` `charge_rates()` composite. Postgres inlines immutable SQL functions, avoiding an extra call cost in the locked transaction. A rates table would require a lookup and make the function `STABLE`. (F22)
- `calculate_charges` returns `(total numeric, breakdown jsonb)`. `execute_order` can then insert `trades.charges` and `trades.charge_breakdown` without casting money. (F22)
- Charge parity is a separate, read-only fourth tier because the TypeScript estimator and Postgres calculator must run in one process. Putting it in tier 3, gated by `ALLOW_RACE_TESTS`, would let a green run skip the feature's main comparison. (F22)
- Use `clock_timestamp()` for `fund_ledger.created_at`, `trades.traded_at` and `orders.placed_at`. `now()` gives every row in one transaction the same time. F28 fills all crossed orders in a run and F29 closes all positions in a run; tied timestamps would make Reports order those trades arbitrarily. (F23, F24)
- The rate table was corrected against Zerodha's published charges on 2026-08-21: NSE transaction charge is 0.00307%, replacing 0.00297%, and ₹15.34 DP already includes GST. `charge_breakdown` records `dp_charge` as ₹13.00 and includes its ₹2.34 GST in the single `gst` key. Adding GST to ₹15.34 would charge it twice on each CNC sell. (F06)
- Calculate GST from unrounded components, then round it once. The same change extended §13's sweep grep to charge terms: searching only margin and P&L identifiers could not find rate drift. (F06)
- The simulator charges DP once per sell order, a deliberate simplification disclosed on `/legal`. Charging once per scrip per day would require `execute_order` to query same-day trades while holding locks. (F06)
- Funds shows realised P&L and reads no prices. Adding unrealised P&L would require quotes, provenance and handling of unpriced symbols to repeat a figure already shown by Dashboard and Holdings. §9 distinguishes the two measures. (F32)
- Dashboard aggregates holdings only; MIS positions appear on `/positions`. This follows Kite's split and avoids trying to draw negative intraday exposure in a donut. (F21)
- Day's P&L is `Σ quantity × (ltp − prev_close)` across holdings, as §9 specifies. It uses the watchlist change column's basis and needs no `trades` read. (F21)
- The watchlist's initial change figure is calculated in a Postgres `security_invoker` view. The panel needs one round trip, and F30 and F33 can reuse the same row shape. (F18)
- Keep charge rates on `/pricing`; Home quotes none. A second copy would create another place to maintain whenever a rate changes. (F04)

## Order entry

- `place_order` returns `INVALID_QUANTITY` without writing an `orders` row. Every other rejection inserts a row and then marks it `REJECTED`, so this refusal alone is absent from Orders → Rejected. Ticket validation blocks it, but direct RPC can reach it. **Not fixed.** (Phase 4 checkpoint)
- The ticket's margin estimate uses the user's actual holding and position through `src/lib/trading/margin.ts`, following §6. Tier 4 checks exact equality with the engine's arithmetic. For a buy covering a short, reserve `opening quantity × price + estimated charges`, not the full order's notional value plus charges; existing collateral already covers the closing quantity. The requirement is exact agreement, not "within one paisa"; the branch-selection gap remains recorded in `constraints/testing.md`. (F25)
- When the ticket opens, fetch the symbol's holding and position in one RLS-scoped query. This avoids sending the entire portfolio with every terminal page and needs one fresh read per opening, not per keystroke. (F25)
- Mount the ticket once in the terminal layout and open it through `useOrderTicket`. F18's watchlist panel renders in both the rail and mobile sheet, so putting a dialog in each row would mount two forms for the same symbol. (F25)
- Close the ticket on rejection. Its order is already recorded as `REJECTED`; keeping the form open would suggest it can still be edited, while each retry creates another order. F25's inline `failure` state is therefore unreachable and is removed. (F26)
- Return a rejection as `ok:false` with its reason in `code`. Only a fault is an abnormal database return. Callers use the normal failure branch and follow `code-standards.md`'s toast rule. (F26)
- Use a `Controller` to map an empty limit-price field to `null` at the field boundary. An uncontrolled `type="number"` can send `''`, `null`, `undefined` or `NaN`, depending on whether the user or `setValue` last wrote it. Since `Number(null)` is 0, users with an empty field were incorrectly told to enter a price above zero. (F25)
- Date filters use the view's `date` column: `trade_history.traded_on` is `(traded_at at time zone 'Asia/Kolkata')::date`. Callers do no timezone arithmetic; the `at time zone` conversion belongs in the view. F33's chart had the reverse UTC/IST problem; a 23:45 IST trade can likewise be filed under the previous day if conversion is wrong. (F34)
- Orders includes rows matching `status=OPEN`, `placed_at` today, or `executed_at` today. The third condition keeps older orders visible when they fill, cancel or reject today. Every terminal transition stamps `executed_at`. Without it, such orders vanished instead of changing tabs. (F27, fixed at the Phase 4 checkpoint)

## Database concurrency

- `match_open_orders` gives each `execute_order` call its own subtransaction. A genuine fault rolls back that order and lets the run continue; otherwise one broken order would block every user's fills on every tick. Business rejections return normally after being recorded as `REJECTED`, so they do not enter this handler. (F28)
- The matcher's selection improves efficiency; `execute_order` makes the correctness decision. It rechecks `status = 'OPEN'` and limit eligibility under the row lock. A bad selection `WHERE` may delay a fill by a tick but cannot cause an ineligible fill. The matcher therefore needs no symbol argument. (F28)
- Take locks in the order `orders` → `funds` → `holdings`/`positions`. `execute_order` establishes that order, and `15-lock-order.sql` reads each live definition to check it. `square_off_mis` once held a position lock across an `execute_order` call and deadlocked. Adding a guard under a row lock changes lock order too. (F29)
- `transfer_margin_to_position` and `recompute_position_collateral` take `positions` before `funds`. They are safe only because `execute_order` already holds both. Any new caller must first hold that user's funds row. F31's exit avoids a new mutation path by placing an order through `place_order` → `execute_order`. (F29, F31)
- Check a sweep's returned counters as well as its final rows. `square_off_mis` and `match_open_orders` catch faults with a `raise warning` and a counter. This swallowed a deadlock (`40P01`), allowing all end-state assertions to stay green after removing the position lock. (F29)
- Before writing an exit order, `square_off_mis` re-reads the position under its own lock. Otherwise two runs can select it, the first closes it, and the second submits an exit against no position. `execute_order` correctly treats that sell as a new short, allowing a 15:20 square-off to create fresh exposure with collateral blocked. (F29)
- The pinned lock order covers one user at a time. Each sweep holds an owner's `funds` row until its run ends, so overlapping sweeps can still form an ABBA deadlock across different users: each waits for a row held by the other. `15-lock-order.sql` cannot detect this. **Not fixed.** (Phase 4 checkpoint)
- `add_watchlist_item` does not serialise `select max(sort_order) + 1`. Two simultaneous adds can receive the same `sort_order`, after which reorder silently does nothing until `move_watchlist_item` renumbers them. **Not fixed:** it needs a row lock and a tier-3 test, which commits into the one real database. (F18)
