## How this file is maintained

This file grows for the life of the project and is **not** part of the session read order.
Nothing here is required to make a decision — anything that still constrains future work gets promoted to `constraints.md`, which is the file consulted during ordinary work.
That separation is what keeps the cost of knowing "what binds" from growing with the length of the build.

- **Append a dated entry after every completed feature**, under the current phase: decisions made, gotchas hit, verification results.

## Phase 5 — Portfolio Pages

### Feature 33 — Stock detail page  *(2026-09-11)*
- Decision: **simulated candles are deterministic, seeded from `(symbol, interval, ts)`.** A free-running walk would redraw a different year of history on every TTL refresh — fabricated data that contradicts itself, which is what the provenance rules exist to prevent. The daily series is bridged so its last close lands on `quotes.prev_close`, the same anchor the live quote simulator walks from (F16), with `instruments.prev_close` as the cold-start fallback. Verified live: the chart's last close and the header's prev close agree to the paisa on every symbol checked.
- Decision, and worth stating precisely because it is easy to get wrong: **purity and immutable history are two different properties with two different owners.** `buildSeries` is pure — same input, same bytes — but the anchor each batch is bridged to moves with the day, so purity alone would not stop a refresh rewriting the past. What actually protects history is the *service*: it generates only the slots it does not already hold, plus the one still forming. The docblock says so rather than claiming the generator does it.
- Decision: **retention is `prune_candles()` on its own `pg_cron` (18:30 UTC daily), not a call inside `market-tick`.** `boundary-patterns.md` sketched the opposite, but that host is F16 — parked until the very end of the project — and a prune living there is only verifiable by deploying and waiting for a tick. As SQL it is tier-2 testable. Both that file and `patterns.md` (which promised a limiter and circuit breaker on this path; F15 already established a bucket in front of a local simulator caps nothing) were corrected in the same change.
- Decision: **the chart draws once per server render and does not tick.** The `FIVE_MIN` TTL means the series is at best five minutes fresh, so a live-growing rightmost bar would imply precision the pipeline does not have — and it keeps a canvas out of F19's trap. Range switching goes through `?range=`, so each range is a server render, the URL is shareable and the switcher works with no JavaScript.
- Decision: **52-week high and low are derived from the stored `ONE_DAY` series**, needing no column and no second fetch. `prune_candles()` keeps 400 days rather than 365 precisely so a prune cannot race the read and shorten the window it reports.
- **Gotcha, and the one that cost the most: two identical GET reads in one render return the same answer, even with a write between them.** `read → upsert → read` rendered an empty chart over 276 rows it had just written. Next memoizes identical `fetch` calls per render pass and supabase-js is built on `fetch`. **`cache: 'no-store'` does not defeat it** — that opts out of the Data Cache, not memoization; I tried it and it changed nothing. Isolated by issuing the same query with one different parameter (`.limit(99999)`), which returned 276 while the identical one returned 0. Fixed by having `refresh` return the merged series it produced, which removes the round trip and the read-after-write dependency together. Promoted to `constraints.md`.
- Gotcha: **Lightweight Charts has no time-zone support and treats every value as UTC** — its own docs say so — so an NSE session drew an axis reading 03:45–10:00 in a browser that was itself in `Asia/Calcutta`. Both time forms are now shifted to IST at the render boundary; the shifted value is a label-only wall clock and `candles.ts` keeps the true UTC instant.
- Gotcha: `interval` is reserved in Postgres and cannot be an OUT column name — `prune_candles()` returns `bar_interval`. It fails to parse rather than shadowing quietly, which is the good outcome.
- **Gotcha in my own test, caught by tier 2 rather than by reading it:** `18-candles.sql` asserted `min(ts)`/`max(ts)` over the whole `candles` table, so it passed only while nothing else was cached. One visit to this page writes a year of real bars including today's, and assertion 9 then answered about those instead of about the prune. Scoped to the fixture symbols and re-falsified.
- Verified: `pnpm test` 433 (47 new — determinism, anchoring, bar shape, slot calendar, TTL boundaries, 52-week window), `pnpm test:db` 23 files with `18-candles.sql` at 14/14, 36 parity, plus lint, typecheck, `format:check` and `build` clean. Both new suites were falsified: seeding with `Math.random` fails determinism, removing the bridge fails the gap assertion, and a single shared retention window fails five retention assertions.
- Verified in the browser, signed in, against the real account: ten symbols render with no chart or hydration errors; 1M↔1Y leaves `candle_sync.fetched_at` byte-identical, as do repeat visits inside the TTL; a cold cache now draws on the *first* load; canvases go 7 → 0 → 7 across four client-side round trips, so `chart.remove()` holds; an unknown symbol is a genuine 404; the SSR HTML carries the real price and the sr-only provenance sentence rather than an em dash (F20); the page does not scroll sideways at 375px on three ranges; the theme toggle re-applies grid and axis colours; and with the chain forced to decline against stale rows the chart still draws beside "Could not refresh. Showing data from 8/9/2026, 10:03:47 pm."
- Not run: **tier 3.** F33 adds no concurrency path — no new lock, no new writer of a user-owned table — and its Verify block does not ask for it.
- Note for whoever adds Yahoo: the `CandleProvider` seam takes the slot list and both anchors, so a real provider can ignore them and return its own history; the service filters. `library-docs.md`'s unverified candle-response-shape TODO is deliberately still open.

### Feature 31 — Positions page  *(2026-09-08, built and green on every automated tier)*

- Decision: **unrealised P&L is one signed expression for both directions** — `net_quantity × (ltp − average_price)`. A short of 100 at ₹99.70 against an LTP of ₹90 gives `−100 × −9.70 = +970`, which agrees with §9's `(average_price − exit_price) × quantity`. A `case` on direction would have been two formulas free to drift, checked by nothing.

- Decision: **no new margin arithmetic.** `src/lib/trading/margin.ts` is already position-aware and proven equal to the engine at tier 4, so a covering buy reserves only its charges (§6) with no change to the module.

Its `position_count` and `unpriced_count` come through `count(col) filter`, since `count(*)` would report the left-joined phantom row that keeps an unpriced position visible.

### Feature 30 — Holdings page  *(2026-09-05)*
- Started ahead of the Phase 4 checkpoint by choice: F27 and F28 are both blocked on market hours and F30's automated tiers were not, so the closed-market day went to the page rather than to waiting.
- **The feature turned out to be a page and a table, not a data feature.** F21 had already built `portfolio_holdings` and `portfolio_summary` with `invested`, `market_value`, `unrealised_pnl`, `day_pnl` and provenance; `(terminal)/layout.tsx` already unioned held symbols into the quote channel *with a comment saying it did so for F30*; `openTicket`'s `quantity` field was already typed for an exit; `06-portfolio.sql` already asserted the view arithmetic against a hand-computed fixture. **No migration, no new SQL for the page.** Reading the always-list before planning is what turned a schema feature into a rendering one.
- Decision: **the whole row jumps on the anchor, LTP included.** `architecture.md` names every total on Holdings as anchor-only, and a sliding LTP beside a current value that waited for the tick puts a row visibly in disagreement with itself. Nothing on the page reads `ltp`; `anchorFor` is the only price source in scope, which makes it structural rather than a convention.
- **Decision, and the real find of the feature: `provenanceOf` describes the store, not the figure on screen.** Its `isInterpolated` is `quote.ltp !== quote.anchor` — true whenever a tween is in flight, whatever the caller chose to render. Since every monetary surface renders the *anchor*, passing it into `PriceWithProvenance` announces "this figure is interpolated between server prices" over a figure that is literally the last price a provider reported. F21's tiles never hit it because a portfolio value is an aggregate with no single quote to attach to, so F30 is the first surface that renders an anchor *through* that component. `anchorProvenance()` is the fix. It takes the three fields it reads rather than a whole `LiveQuote`, because the F19 rule against subscribing to `state.quotes` means its callers hold flat maps of primitives and never a whole quote — the loose shape is a consequence of that constraint, not a preference.
- Decision: **the footer comes from `portfolio_summary` through the existing `recomputeSummary`, not from summing rows in TypeScript.** Postgres does the arithmetic per the money rule, and rows and footer are then driven from one `useHoldingPrices` call, so a tick that moves a row moves the total in the same render. They cannot drift.
- Decision: **`invested` became a row column so the footer's invested total has something above it to be the sum of.** The build plan listed it as a footer figure with no matching row column; a total that aligns under nothing cannot be read as a total. One `<td>` reading a value the view already computes.
- Decision: **an unpriced holding sorts last in both directions.** Treating its null as negative infinity would head an ascending P&L sort with it, reading as the worst performer in the portfolio when nothing at all is known about it — the misreading the em dash exists to prevent, reintroduced through the ordering.
- Tidy: `use-holding-prices.ts` moved from `components/dashboard/` to `components/terminal/`, since the boundaries table gives `terminal/` the quote store and both consumers now sit under it.
- Gotcha: **the new pgTAP section broke four assertions in a section it never touched.** `reset_account()` acts on `auth.uid()`, and `pg_temp.place` sets that claim for whoever it places as — so a new section placing an order for Ao *before* section L silently redirected L's reset from Bo onto Ao. Moved to the end of the file, after L, with the reason recorded in the section header. **The coupling is invisible at the call site**: L never names a user, it inherits one.
- Gotcha: the zero-quantity assertion needed two halves. `holdings` carries `CHECK (quantity > 0)`, so a build that tried to leave a zero row would raise rather than write one, and the order would come back REJECTED with the row still holding 20 — `is_empty` alone passes on a build where the sell simply failed. Asserting the fill *and* the empty table is what separates the two, which is the F29 lesson applied at tier 2.
- Correction to the plan, found late: **F30's populated-table browser checks do need market hours after all.** The account holds nothing, and a holding can only exist once a CNC buy fills. Four browser items therefore join Monday's errand rather than being independent of it, and the box is left unticked.

Both new assertions were falsified before being trusted: selling 19 of 20 leaves the row and fails the `is_empty`; adding `+ 1` to `recomputeHolding`'s market value fails the footer-equals-rows test while `recomputeSummary` is untouched, which is also what proves the two are independent code paths rather than one expression asserted against itself.

(F23, F24)
- **Session logic is implemented exactly twice and proven equal at tier 4**, because `place_order` is granted to `authenticated` and a gate living only in a Server Action is bypassed by a direct RPC. A third implementation is not permitted. (F24)
- **Tier 4 exists because of this phase** — a read-only fourth tier proving the TypeScript estimator and the Postgres calculator exactly equal, placed outside the `ALLOW_RACE_TESTS` gate so the headline test cannot be skipped inside a green run. The bar was measured before it was chosen, and "within one paisa" was tightened to exact. (F22, F25)
- **F25's lesson was that every arithmetic path was green while the form was unusable** — the empty-limit-price case reached the schema as four different values depending on who wrote last. Tier 1 cannot see a form. (F25)
- **F26 found that the first order ever placed through the app broke `pnpm test:db` permanently**, on a reference-table FK: a failing test tier caused by using the product. (F26)
- **The matcher adds no fill logic and no pricing** — `match_open_orders` selects and delegates, one subtransaction per order, and its `WHERE` is an optimisation rather than a correctness boundary because `execute_order` re-checks everything under the lock. (F28)
- **F29's real find was that a guard added under a row lock is also a change to lock order.** The position re-read that closed one race inverted `orders → funds → positions` and made the 15:20 sweep the one path acquiring the pair backwards. The deadlock was invisible because `exception when others` counted the `40P01` as a fault — which is why a race test must assert what a sweep *returns*, not only what it left behind. (F29)
- **A closing leg is never rejected for want of funds, and `execute_order` did not implement it.** The solvency check demanded `available_cash >= charges` even with no opening leg, stranding a second underwater short past 15:20. The checkpoint later narrowed the guarantee: it covers pure covers and square-offs, never a fill that also opens exposure, because §1 forbids the partial fill that would be needed. (F29, checkpoint)

## Phase 3 — Terminal Shell & Live Prices *(compacted 2026-08-22 at the Phase 3 checkpoint)*

Features 17–21 built the signed-in terminal: shell, watchlist, live quote store, provenance, dashboard.

- **The shell owns the singletons, and pages beneath it own nothing.** The session is checked once in `(terminal)/layout.tsx`; one Realtime channel and one `requestAnimationFrame` driver are mounted there so both survive navigation. The rail lives beside `<main>` and only the sheet trigger sits in the nav — one component rendering both put a 288px `aside` inside a 64px header row. (F17, F18, F19)
- **`anchor` is the truth and `ltp` may be synthetic**, and the split is now enforced by shape as well as by rule: the dashboard's helpers take flat maps of anchors, so there is no `ltp` in scope for a total to read by mistake. The interpolation loop tweens *between* server anchors and invents nothing — an earlier draft specified bounded jitter, which would have put figures on screen that no provider reported. (F19, F21, 3.00.01)
- **Provenance is derived at read time and announced, never merely hovered.** One ticking clock from the layout so the badge cannot contradict the row it summarises; `sr-only` text tied by `aria-describedby` because hover does not exist on touch; only STALE is muted, since muting SIMULATED would grey the whole terminal and stop carrying information. ### Feature 11 — Database schema: funds, orders, and portfolio  *(2026-08-21)*
- Decision: **the money tables grant `select` and nothing else.** No client role holds insert, update or delete on any of the six, and no write policy exists — every write arrives through a `security definer` function. `code-standards.md` already forbade a Server Action writing them directly, so a write grant would have existed only to be unused.
- Decision: **three §12 identities encoded as CHECK constraints** — 8 (a non-`OPEN` order holds no margin), 12 (longs hold no collateral and no reference price, shorts carry both) and 6 (`charge_breakdown` sums exactly to `charges`) — alongside all-or-nothing fills, `limit_price` presence, and the zero-quantity rules.
- Decision: **that choice constrains F23/F24, and `code-standards.md`'s `execute_order` example was corrected for it.** A CHECK is not deferrable, so setting `status = 'REJECTED'` and *then* calling `release_margin` — exactly what that example did — now fails on the first statement with 23514. The margin must be retired before the status leaves `OPEN`, which is the ordering the contract already implied. A new rule in code-standards states it directly.
- Decision: foreign keys cascade from `orders` and from `profiles`; `reset_account` still deletes each table explicitly per §11, so the cascade is a backstop rather than the mechanism.
- **Finding — a CHECK constraint passes when its expression evaluates to NULL, and identity 6 was bypassable because of it.** The sum check reads seven keys with `->>`; a missing key yields NULL, the sum becomes NULL, the comparison becomes NULL, and the row is accepted. Observed, not theorised: a trade with `charges = 999.99` and a breakdown of `{"brokerage":0}` was stored without complaint. §12.6 was being enforced only for rows that already had every component — precisely the rows that were never going to violate it.
- **Gotcha — the first fix reproduced the same defect one level up.** A shape check reading `jsonb_typeof(... -> 'stt') = 'number'` also goes NULL for an absent key, so `true and NULL` is NULL and the constraint passed exactly as before. ### Feature 10 — Database schema: identity and market data  *(2026-08-21)*
- Decision: **only the two enums this migration's tables reference.** `order_side`, `order_type`, `product_type`, `order_status` and `ledger_type` are created by F11 alongside the tables that use them, so each migration reviews against what it creates and nobody reading the schema in between finds five types with no referents.
