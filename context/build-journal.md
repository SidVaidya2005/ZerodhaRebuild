## How this file is maintained

This file grows for the life of the project and is **not** part of the session read order.
Nothing here is required to make a decision — anything that still constrains future work gets promoted to `constraints.md`, which is the file consulted during ordinary work.
That separation is what keeps the cost of knowing "what binds" from growing with the length of the build.

- **Append a dated entry after every completed feature**, under the current phase: decisions made, gotchas hit, verification results.
- **Compact at every phase checkpoint, never continuously.** When a phase closes:
  1. **Promote** anything from that phase that still binds into `constraints.md`, filed under its topic.
  2. **Collapse** the phase's per-feature entries into a handful of summary bullets.
  3. **Drop every `Verified:` line** — it has done its job once the next feature passes.
- Only the current phase keeps full per-feature detail. Earlier phases stay compacted, newest first.

Compaction is recoverable: this file is committed, so `git` history holds every detail ever removed.

### Feature 15 — Quote provider chain  *(2026-08-21)*
- Decision: **the simulator walks from a real NSE close.** `library-docs.md` said it seeds "from `instruments` reference data", but that table carried no price — a cold start had nothing to walk from and every symbol would have begun at an invented constant. `instruments.prev_close` is now seeded from the published bhavcopy, found on the **archive** host that F14 already reaches rather than the API that answers 403. MRF opens near ₹1,32,665 and YESBANK near ₹22.80; a shared constant would have priced them identically and made Phase 5's portfolio arithmetic meaningless.
- Decision: **the close is a seed, never a quote.** No `NSE_BHAVCOPY` value joins `quote_provider`, nothing writes it into `quotes`, and no surface renders it as a price. Every price still comes from a row carrying `provider = 'SIMULATOR'` and a null `provider_ts`, which `deriveSource()` renders as SIMULATED. Nullable on purpose: a fresh listing with no close makes the simulator report itself **unavailable** rather than creative.
- Decision: **the seam is built, the limiter is not.** `QuoteProvider`, an ordered chain and a per-provider circuit breaker, exercised against a deliberately failing fake. A token bucket in front of a local simulator caps nothing, so it waits for a provider that makes outbound requests. F14 is why the breaker earns its place now: the failure that mattered was not one bad response but continuing to hammer an upstream that had already said no, which is what kept Yahoo's block alive for forty minutes.
- Decision: **`market-hours.ts` is a pure core with database-backed wrappers.** `marketStatusAt(date, holidays)` takes its calendar as an argument so tier 1 can falsify it; `isTradingSession(supabase, at)` and `getMarketStatus(supabase, at)` load and delegate. `loadHolidays` **throws** rather than returning an empty set on a read error — an empty calendar is indistinguishable from a year with no holidays, and the failure it causes (trading on Republic Day, a square-off that never runs) is otherwise silent.
- Decision: **Asia/Kolkata is treated as a fixed UTC+05:30.** India has observed no daylight saving since 1945, so this is exact rather than an approximation — and the assumption is *checked*, not asserted: a test compares the arithmetic against `Intl` at five instants across the year, including both hemispheres' DST changes.

### Feature 11 — Database schema: funds, orders, and portfolio  *(2026-08-21)*
- Decision: **the money tables grant `select` and nothing else.** No client role holds insert, update or delete on any of the six, and no write policy exists — every write arrives through a `security definer` function. `code-standards.md` already forbade a Server Action writing them directly, so a write grant would have existed only to be unused.
- Decision: **three §12 identities encoded as CHECK constraints** — 8 (a non-`OPEN` order holds no margin), 12 (longs hold no collateral and no reference price, shorts carry both) and 6 (`charge_breakdown` sums exactly to `charges`) — alongside all-or-nothing fills, `limit_price` presence, and the zero-quantity rules.
- Decision: **that choice constrains F23/F24, and `code-standards.md`'s `execute_order` example was corrected for it.** A CHECK is not deferrable, so setting `status = 'REJECTED'` and *then* calling `release_margin` — exactly what that example did — now fails on the first statement with 23514. - Decision: foreign keys cascade from `orders` and from `profiles`; `reset_account` still deletes each table explicitly per §11, so the cascade is a backstop rather than the mechanism.
- **Finding — a CHECK constraint passes when its expression evaluates to NULL, and identity 6 was bypassable because of it.** The sum check reads seven keys with `->>`; a missing key yields NULL, the sum becomes NULL, the comparison becomes NULL, and the row is accepted. Observed, not theorised: a trade with `charges = 999.99` and a breakdown of `{"brokerage":0}` was stored without complaint. §12.6 was being enforced only for rows that already had every component — precisely the rows that were never going to violate it.
- **Gotcha — the first fix reproduced the same defect one level up.** A shape check reading `jsonb_typeof(... -> 'stt') = 'number'` also goes NULL for an absent key, so `true and NULL` is NULL and the constraint passed exactly as before. Caught only because the probe was re-run after applying it rather than assumed fixed. The working form wraps each in `coalesce(..., '')`, and this time the expression was evaluated against four malformed documents in a plain `SELECT` **before** being written into a migration. Three migrations rather than one, and the history shows why.
- Gotcha: the `orders_limit_price_iff_limit` constraint caught the seed data for the index benchmark — LIMIT rows inserted without a price, intending to set it in a follow-up `UPDATE`. The constraint working on its author is a reasonable first customer.
- Gotcha: dropping `positions_collateral_on_shorts_only` reddens its own assertion *and* the §12.11 positive control further down, because the row the first case now successfully inserts collides on the primary key with the row the control tries to insert. Worth knowing before reading a falsification result as two separate failures.
- Verified **by falsification, seven ways**, each break inside a transaction that rolls back so the production schema is never left modified: dropping identity 8, identity 12, identity 6 and the breakdown shape check each reddens its named assertion; dropping `funds_read_own` reddens the owner-read case; granting `authenticated` update on `funds` reddens both the refusal case and the "SELECT and nothing else" grant assertion. Replacing the trades cascade with a plain foreign key turns the suite red through a 23503 on the DELETE rather than a `not ok` — red either way, and recorded as what it is rather than rounded up.
- Verified: four migrations applied cleanly, a second push reports up to date, `migration list` shows five entries. Types regenerated — 15 tables, 7 enums, no `: any`.
